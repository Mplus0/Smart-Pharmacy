# Smart Pharmacy 比赛代码结构与策略梳理

## 1. 比赛规则要点

智慧药房比赛模拟“体检区”到“化验区”的样本配送任务。场地包含：

- 体检区：A、B、C 三个窗口。
- 化验区：1、2、3、4 四个窗口。
- 识别板一：四个二维码方框，每个方框对应一个化验窗口。
- 识别板二：显示化验区状态，提示空闲或忙碌等待时间。

化验窗口与样本类型的对应关系为：

| 化验窗口 | 窗口名称 | 样本类型 |
| --- | --- | --- |
| 1 | 血常规窗口 | 静脉血样本 |
| 2 | 体液窗口 | 唾液样本 |
| 3 | 免疫检测窗口 | 组织样本 |
| 4 | 激素检验窗口 | 血浆样本 |

识别板一的二维码内容决定需要去哪些体检窗口取样：

- `A` / `B` / `C`：单窗口取样。
- `AB` / `AC` / `BC`：双窗口取样。
- `ABC`：三窗口取样。

二维码所在方框决定最终配送到哪个化验窗口。例如：方框 1 中二维码为 `AB`，表示从 A、B 取静脉血样本，并送到化验区 1 号血常规窗口。

识别板二规则：

- “化验区空闲中，请快速通过”：需要播报，并在 3 秒内尽快通过。
- “化验区忙碌中，需等待 n 秒”：`n` 为 5-10，需播报并等待对应时间后通过。

主要得分策略：

- 一次性配送一个二维码中的全部样本有加成：
  - 三个样本一次性送达：+25。
  - 两个样本一次性送达：+15。
  - 一个样本送达：+5。
- 识别板二动作正确并完成播报：+3。
- 体检区、化验区播报符合格式：每次 +1。
- 局域网实时传输状态信息可得通信分：速度、里程计、视觉识别结果、位置、当前任务。
- 双车轮流配送有总分 1.5 倍加成，但当前主要是单车策略，双车只预留接口。

## 2. `pharmacy_v5` 包结构

`pharmacy_v5` 是当前主程序功能包，核心目录如下：

```text
pharmacy_v5/
├── launch/
│   ├── main.launch              # 比赛模式：识别、主控、TCP 全部启动
│   ├── main_single.launch       # 单车调试/比赛：静默语音，保留 TCP
│   ├── debug_detection.launch   # 只跑识别和 TCP，小车不动
├── scripts/
│   ├── F1_yaofang.py            # 主控状态机
│   ├── F1_detect_code.py        # 识别板一二维码识别，参考旧包初始策略
│   ├── F1_detect_code_1.py      # 识别板一融合版历史脚本，暂不作为重构目标
│   ├── F1_detect_code_ROI.py    # ROI 版历史脚本，当前重构暂不采用
│   ├── board2_detector.py       # 识别板二状态模板匹配
│   ├── competition_helper.py    # 比赛任务、播报、样本记录、上报封装
│   ├── tcp_reporter.py          # TCP 状态上报与语音播报
│   ├── detection_monitor.py     # 调试监视器
│   └── log_utils.py             # 中文日志封装
└── templates/
    └── board2/
        ├── idle.png
        ├── wait5.png
        ├── ...
        └── wait10.png
```

旧包 `smart_pharmacy` 和 `pharmacy_pkg` 主要保留了早期导航状态机、固定航点、识别与音频播报逻辑。`pharmacy_v5` 已将这些逻辑重构为状态机主控、视觉节点、竞赛辅助模块和 TCP 上报模块。

## 3. 系统数据流

当前系统以 ROS 话题连接各模块：

```text
摄像头视频流
  ├─> F1_detect_code*.py
  │     ├─ 发布 /cam_return      Int32MultiArray
  │     └─ 发布 /all_qrcodes     String(JSON)
  │
  └─> board2_detector.py
        └─ 发布 /cv1_result      String, 如 WAIT-0 / WAIT-8

F1_yaofang.py 主控
  ├─ 订阅 /cam_return
  ├─ 订阅 /cv1_result
  ├─ 发布 /reset_detection
  ├─ 调用 move_base 导航
  └─ 通过 CompetitionHelper 发布：
        /current_task
        /cv1_result
        /cv2_result
        /announce_request
        /current_qr_task

tcp_reporter.py
  ├─ 订阅 /odom
  ├─ 订阅 /current_task
  ├─ 订阅 /cv1_result
  ├─ 订阅 /cv2_result
  ├─ 订阅 /announce_request
  ├─ 查询 TF: map -> base_footprint
  └─ TCP 发送 JSON 到裁判系统
```

TCP 上报 JSON 当前字段：

```json
{
  "id": "1",
  "speed": 0.123,
  "odom": [1.234, 2.345],
  "task": "A",
  "CV1": "WAIT-8",
  "CV2": "AB-1"
}
```

其中：

- `task`：`A/B/C` 表示停在体检窗口，`1/2/3/4` 表示停在化验窗口，`R` 表示路上、起点或识别区。
- `CV1`：识别板二结果，`WAIT-0` 表示空闲，`WAIT-5` 到 `WAIT-10` 表示忙碌等待秒数。
- `CV2`：识别板一任务结果，如 `AB-1` 表示取 A、B 样本并送 1 号化验窗口。

## 4. 主控状态机

`scripts/F1_yaofang.py` 是比赛主控程序，使用 11 个状态完成循环配送：

| 状态 | 功能 |
| --- | --- |
| `S_INIT` | 初始化任务状态、清空样本记录 |
| `S_GOTO_BOARD1` | 前往识别板一 |
| `S_AT_BOARD1` | 等待二维码识别结果 |
| `S_GOTO_EXAM` | 前往下一个体检窗口 |
| `S_AT_EXAM` | 停在体检窗口、记录取样、必要时播报 |
| `S_GOTO_BOARD2` | 前往识别板二 |
| `S_AT_BOARD2` | 等待化验区状态识别并播报 |
| `S_PASS_BOARD2` | 空闲快速通过，忙碌等待后通过 |
| `S_GOTO_LAB` | 前往目标化验窗口 |
| `S_AT_LAB` | 停在化验窗口、播报、投递样本 |
| `S_DONE_ROUND` | 本轮结束，清空任务，进入下一轮 |

单轮任务流程：

```text
前往识别板一
  -> 识别二维码
  -> 选择最优二维码任务
  -> 规划体检窗口访问顺序
  -> 依次前往 A/B/C 取样
  -> 前往识别板二
  -> 识别空闲/忙碌并播报
  -> 按规则快速通过或等待
  -> 前往对应化验窗口
  -> 播报样本数量并投递
  -> 直接开始下一轮
```

主控不会在每轮结束后回起点，而是直接回到识别板一开始下一轮，目的是节省 4 分钟比赛时间内的往返成本。

## 6. 识别板一策略

识别板一由 `F1_detect_code*.py` 负责，输出 `/cam_return`：

```text
data = [is_C, is_A, is_B, count, box_idx, error_code]
```

字段含义：

- `is_C/is_A/is_B`：二维码内容是否包含对应体检窗口。
- `count`：样本数量，即二维码字母个数。
- `box_idx`：二维码所在方框索引，0-3 对应化验窗口 1-4。
- `error_code`：占位字段，当前正常为 0。

主控将该结果转换为：

- `target_code_str`：如 `A`、`AB`、`ABC`。
- `target_lab_window`：`box_idx + 1`。
- `sample_type`：由化验窗口号映射得到。
- `windows_to_visit`：本轮需要依次访问的体检窗口列表。

当前选择策略：

- 识别节点会从同帧多个二维码中选择最优任务。
- 优先级按样本数最大化：`ABC` 优先，其次双窗口组合，再其次单窗口。
- 这样符合一次性配送加分规则，优先争取 +25，其次 +15，再其次 +5。

当前访问顺序表：

| 二维码 | 访问顺序 |
| --- | --- |
| `A` | A |
| `B` | B |
| `C` | C |
| `AB` | A -> B |
| `AC` | C -> A |
| `BC` | C -> B |
| `ABC` | C -> A -> B |

该顺序是按当前场地航点和曼哈顿距离经验制定的最短顺序。

当前决定采用的识别板一初始策略参考 `pharmacy_pkg/scripts/detect_code_for_EPRobot.py`，暂时不使用 ROI 优先或三层融合方案。实现流程为：

- 对摄像头画面做必要的小角度旋转校正。
- 灰度化后使用 Canny 做边缘检测。
- 按轮廓面积筛选候选轮廓。
- 对候选轮廓做四边形近似，保留四边形。
- 用长宽比/边长差筛选近似正方形。
- 通过嵌套正方形的中心重合关系筛出二维码定位框。
- 定位框数量满足条件后，用极值点推算识别板四角。
- 使用透视变换将识别板矫正到固定画布。
- 在矫正图中按四个固定区域裁剪方框 1-4。
- 对四个裁剪区域二值化并调用 `pyzbar.decode` 解码。
- 将解码内容和方框编号转换为 `/cam_return` 或标准化识别结果。

因此，后续重构时 `board1_decoder.py` 应优先实现“定位框轮廓筛选 + 透视矫正 + 四区域裁剪 + pyzbar 解码”的初始方案。`F1_detect_code_1.py` 和 `F1_detect_code_ROI.py` 可作为历史参考保留，但不作为当前主策略；如果现场效果不好，再单独新增优化版本。

## 7. 识别板二策略

识别板二由 `board2_detector.py` 负责，基于模板匹配识别状态：

- `idle.png` -> `WAIT-0`
- `wait5.png` -> `WAIT-5`
- ...
- `wait10.png` -> `WAIT-10`

实现特点：

- 从摄像头视频流读取帧。
- 对模板做多尺度匹配。
- 达到匹配阈值后进入去抖队列。
- 连续多帧一致后锁定结果。
- 发布 `/cv1_result`。

主控处理逻辑：

- 若收到 `WAIT-0`：播报“化验区空闲中,请快速通过”，然后直接进入去化验窗口阶段。
- 若收到 `WAIT-5` 到 `WAIT-10`：播报“化验区忙碌中,需等待 n 秒”，等待 n 秒后进入化验窗口阶段。
- 若 10 秒内没有识别到结果：按空闲处理，避免卡死。

## 8. 播报与上报策略

`competition_helper.py` 统一封装比赛相关状态，避免主控直接散落发布话题。

主要职责：

- 发布当前任务：`/current_task`。
- 发布识别板二结果：`/cv1_result`。
- 发布识别板一任务结果：`/cv2_result`。
- 发布语音播报请求：`/announce_request`。
- 记录当前携带样本类型和取样窗口。
- 预留双车协作任务广播：`/current_qr_task`。

当前播报格式：

- 体检区取样完成：`取到 A、B 窗口的样本`
- 识别板二空闲：`化验区空闲中,请快速通过`
- 识别板二忙碌：`化验区忙碌中,需等待 8 秒`
- 到达化验区：`到达血常规窗口，样本数为 2`

`tcp_reporter.py` 同时负责：

- 以 1-2 Hz 频率向裁判系统发送 JSON。
- 异步 TCP 连接和断线重连。
- 通过 TF 查询 `map -> base_footprint` 得到全局位置。
- 读取 `/odom` 中的速度。
- 订阅 `/announce_request` 并调用 TTS 播报。

## 9. 容错策略

当前代码针对比赛现场不稳定因素做了以下保护：

- 识别板一到达后先等待 1 秒稳定画面。
- 识别板一单次等待 15 秒，最多重试 3 次。
- 连续 5 轮识别板一失败后原地停车，等待人工检查。
- 每轮开始发布 `/reset_detection`，清空识别节点锁定状态。
- 识别板二 10 秒未识别到结果时按空闲处理。
- 前往识别板一失败会保持状态并自动重试。
- 前往某个体检窗口失败会跳过该窗口，尝试后续窗口。
- 前往化验窗口失败则结束本轮。
- 每段导航后清理 `move_base` costmap。

## 10. 当前比赛策略总结

当前 `pharmacy_v5` 的核心策略可以概括为：

1. 以单车连续循环配送为主，不回起点，最大化 4 分钟内有效轮次。
2. 识别板一优先选择样本数量最多的二维码，以争取一次性配送加成。
3. 一个二维码对应一轮任务，一轮只携带一种样本类型。
4. 方框号直接决定化验窗口和样本类型，二维码字母决定体检窗口集合。
5. 体检窗口按固定最短顺序访问，减少路径长度和转向成本。
6. 到达体检和化验窗口后停留 1.5 秒，满足“明显停留”和进入方框要求。
7. 所有裁判可见状态通过 `competition_helper.py` 统一发布。
8. TCP 上报持续运行，即使裁判电脑暂时未连接也不阻塞主程序。
9. 识别板二按规则播报和等待，识别失败时选择不中断任务的保守策略。
10. 双车协作接口已有话题预留，但当前单车主流程尚未真正避让对方任务。

## 11. 重构实现建议

后续重构时，可以按“比赛业务”和“工程基础能力”拆分模块：

```text
pharmacy_v5/
├── config/
│   ├── waypoints.yaml          # 航点、朝向、窗口映射
│   ├── strategy.yaml           # 超时、停留、访问顺序、选择权重
│   └── tcp.yaml                # 裁判系统 IP、端口、车号
├── launch/
├── scripts/
│   ├── main_controller.py      # 只保留状态机
│   ├── task_planner.py         # 二维码任务选择和路径顺序规划
│   ├── navigation_client.py    # move_base 封装
│   ├── sample_store.py         # 样本携带与投递记录
│   ├── announcer_client.py     # 播报格式封装
│   ├── reporter_client.py      # current_task/CV1/CV2 发布封装
│   ├── board1_decoder.py       # 识别板一初始透视矫正解码核心
│   ├── board1_detector.py      # 识别板一 ROS 节点
│   ├── board2_detector.py      # 识别板二
│   └── tcp_reporter.py
└── templates/
```

推荐模块边界：

- 主控状态机只关心“当前状态”和“下一步动作”，不直接拼接播报文本。
- 任务规划模块负责从二维码集合中选任务，可扩展双车避让策略。
- 导航模块统一处理目标点、超时、取消、清 costmap。
- 样本模块只记录当前携带的样本类型、窗口列表、投递数量。
- 裁判上报模块统一维护 `task/CV1/CV2`，避免多节点重复发布导致状态覆盖。
- 视觉识别模块输出稳定、简单的数据结构，不参与业务决策。

重构后的主循环仍应保持当前比赛策略：

```text
识别板一
  -> 选最高收益二维码
  -> 一次性取完该二维码对应全部体检窗口
  -> 识别板二动作得分
  -> 对应化验窗口投递
  -> 下一轮
```

这套策略与当前规则的加分项最匹配，且实现复杂度适合单车稳定完成比赛。
